التقرير الهندسي الشامل – مشروع tlbaty

تقييم الأخطاء والترابط والأداء ونتائج الاختبارات الفعلية، وخطة الانتقال من Sanity إلى PostgreSQL وCloudflare R2 · التاريخ: 2026-10-20 · الفرع: claude/project-performance-review-cihgin

تنبيه حول نطاق الفحص: لم يصلني ملف تقرير مرفق، وفحصت المستودع نفسه. حالته الحالية قالب Next.js أساسي من v0 (21 ملفًا، منها 9 أصول في public/). لا يوجد فيه Sanity ولا منتجات ولا طلبات ولا إشعارات ولا رفع صور. لذلك تغطي أقسام الفحص الكود الموجود فعليًا، ويغطي قسم الانتقال التصميم المقترح للمرحلة القادمة. إن أرسلت الكود الفعلي لمشروعك الأصلي (مع Sanity) أُحدّث التقرير عليه.

4. أنواع الأخطاء المرصودة

  • أخطاء إعداد: ignoreBuildErrors وimages.unoptimized وlang بلا dir.
  • أخطاء سلسلة التوريد والأمان: 66 ثغرة في التبعيات، ومعظمها عبر shadcn (مسارات .>shadcn>…) وبعضها عبر next وpostcss (browserslist وsource-map-js وnanoid).
  • أخطاء عملية وجودة: قفل غير متزامن، لا اختبارات، لا lint، لا CI.
  • أخطاء محتوى: نصوص وبيانات meta من القالب.
  • أخطاء تشغيل أو أنواع أو استيراد: لم يُرصد أي منها (tsc نظيف والبناء ناجح).

6. الأداء

  • الوضع الحالي جيد: مساران ثابتان، وبناء 4.1 ث، ولا JavaScript عميل ثقيل.
  • مخاطر مستقبلية: images.unoptimized سيضر بـ LCP عند إضافة صور المنتجات. لا طبقة بيانات أو تخزين مؤقت بعد.
  • توصيات للمرحلة القادمة: Server Components افتراضيًا، وunstable_cache/revalidateTag أو ISR لصفحات المنتجات، وpagination على مستوى SQL، وفهارس مناسبة، وpooling للاتصال (Neon pooler أو PgBouncer)، وتحميل الصور عبر CDN مع next/image.

7. خطة الانتقال من Sanity إلى PostgreSQL + R2

المرحلة 0 – تثبيت الأساس (يوم 1)

  • إصلاح البنود 1 و2 و3 و4 من جدول المشكلات.
  • إضافة CI: lint وtypecheck وtest وbuild.

المرحلة 1 – قاعدة البيانات (أيام 2–4)

  • المزوّد: Neon أو Supabase (PostgreSQL مُدار، يعمل مع Next.js serverless عبر pooler).
  • ORM: Drizzle ORM مع drizzle-kit للـ migrations (خفيف وآمن الأنواع).
  • الهيكل: lib/db/schema.ts وlib/db/client.ts وlib/queries/*.ts وdrizzle/ للـ migrations.
  • الوصول إلى البيانات من Server Components وServer Actions فقط، دون كشف سلسلة الاتصال للعميل.

مخطط الجداول المقترح

categories      (id uuid PK, slug text UNIQUE, name text, parent_id uuid FK→categories)
products        (id uuid PK, slug text UNIQUE, name text, description text,
                 price_minor int NOT NULL, currency char(3), stock int, status text,
                 category_id uuid FK, created_at, updated_at)
product_images  (id uuid PK, product_id FK ON DELETE CASCADE, object_key text,
                 alt text, sort_order int)
customers       (id uuid PK, email citext UNIQUE, name text, phone text, created_at)
orders          (id uuid PK, customer_id FK, status text, total_minor int,
                 currency char(3), created_at, updated_at)
order_items     (id uuid PK, order_id FK ON DELETE CASCADE, product_id FK,
                 qty int CHECK(qty>0), unit_price_minor int)
notifications   (id uuid PK, user_id/customer_id FK, type text, payload jsonb,
                 read_at timestamptz NULL, created_at)

الفهارس: products(slug), products(category_id,status), orders(customer_id,created_at DESC),
         order_items(order_id), notifications(customer_id, read_at) WHERE read_at IS NULL
الأسعار تُخزَّن بأعداد صحيحة بالوحدة الصغرى (أو numeric(12,2)) لتفادي أخطاء الفاصلة العائمة. تُنفَّذ عملية إنشاء الطلب داخل معاملة واحدة تخصم المخزون وتُدخل order_items وتنشئ الإشعار.

المرحلة 2 – الصور على Cloudflare R2 (أيام 4–6)

  • التوصية: R2 وليس PostgreSQL للصور: لا رسوم egress، وتقديم عبر CDN، ولا تضخّم للقاعدة والنسخ الاحتياطية. تُخزَّن في القاعدة object_key فقط.
  • الرفع عبر presigned PUT URLs من Server Action (مكتبة @aws-sdk/client-s3 المتوافقة مع R2)، مع تحقق من النوع والحجم.
  • العرض عبر next/image مع images.remotePatterns لنطاق R2 العام أو نطاق مخصص.
  • إن كانت الصور صغيرة وقليلة جدًا فيمكن البدء بـ bytea، لكن لا أنصح به للمنتجات.

المرحلة 3 – ترحيل بيانات Sanity (أيام 6–8)

  • تصدير: sanity dataset export (NDJSON + الأصول).
  • سكربت تحويل ينقل المستندات إلى الجداول أعلاه (تحويل slugs، والمراجع إلى مفاتيح أجنبية، وblock content إلى نص أو Markdown).
  • رفع الأصول إلى R2 مع الحفاظ على المراجع، ثم تشغيل سكربت تحقق يقارن الأعداد والمجاميع.
  • تشغيل متوازٍ لفترة قصيرة ثم فصل Sanity وحذف حزمه ومتغيراته.

المرحلة 4 – الإشعارات والتشغيل (أيام 8–10)

  • جدول notifications مع استعلام بفهرس جزئي لغير المقروء. البداية بـ polling خفيف أو SSE، ويمكن الترقية لاحقًا إلى LISTEN/NOTIFY أو Realtime.
  • نسخ احتياطي تلقائي (PITR)، ومراقبة الاستعلامات البطيئة (pg_stat_statements)، وحدود للاتصالات.
  • أمن: مفاتيح الوصول في متغيرات بيئية فقط، وصلاحيات أدنى لحساب R2، وRLS إن استُعملت Supabase.

معايير القبول

  • pnpm audit --prod بلا ثغرات عالية أو حرجة.
  • tsc وlint والاختبارات تمر في CI، والبناء بلا ignoreBuildErrors.
  • تطابق أعداد المنتجات والطلبات بعد الترحيل 100%.
  • زمن استعلام قائمة المنتجات أقل من 100 مللي ثانية على بيانات اختبار بحجم الإنتاج.

8. استراتيجية تقليل استهلاك التوكن (Project Indexing)

  • قُرئ المستودع كاملًا مرة واحدة في هذه الجلسة (21 ملفًا)، والخريطة أعلاه (قسم 5) هي الفهرس المعتمد، ولن تُعاد قراءة هذه الملفات في الطلبات القادمة إلا عند تغييرها.
  • عند كبر المشروع: بحث انتقائي (Grep وGlob) بدل قراءة الملفات كاملة، وقراءة مقاطع محددة فقط.
  • الاحتفاظ بملف CLAUDE.md يلخّص البنية والأوامر والقرارات المعمارية (أستطيع إنشاءه عند الطلب).

9. الخطوات التالية المقترحة

  1. تنفيذ إصلاحات المرحلة 0 (دقائق، وبلا مخاطرة).
  2. اختيار المزوّد (Neon أم Supabase) لأبدأ بهيكل Drizzle.
  3. إرسال كود المشروع الأصلي وبيانات Sanity لبناء سكربت الترحيل الفعلي.
